Modifying the Jellyfin Web UI on v12.0.0

Analysis report — reference-UI breakdown, what changed in v12, and a plugin/build plan to get there.

Old CSS/JS skin plugins: mostly broken Plugin ABI: rebuilt for .NET 10 / 12.0.0.0 Custom CSS + theme variables: still supported

1. What the reference video actually is

I pulled frames from jellyfin_ui.mp4 across its ~100s length. It's a Netflix/Apple‑TV‑style reskin of what is structurally still a fairly standard Jellyfin "Modern" home + detail + player flow — the row layout, hover metadata, search overlay and player controls all map onto stock Jellyfin concepts, just heavily restyled and simplified. That's good news: this is very achievable without forking the whole client.

2. The version reality: "v12.0.0" is a real, very new release

Jellyfin dropped the leading 10. from its versioning starting with this release: what would have been 10.12.0 shipped on 2026‑09‑07 as plain 12.0.0. This wasn't a rename for its own sake — it lines up with the biggest architectural shift the web client has had in years, which is exactly why UI-mod plugins built for 10.11 and earlier don't apply anymore.

The two changes that matter for UI work

  • The "Modern" layout is now the default. What used to ship as the opt-in "experimental" layout (a React/MUI rebuild of the client, living under src/apps/experimental in jellyfin-web) is now just called Modern and is the default on desktop and mobile. The old jQuery/Emby-era layout still exists but is now called Legacy and isn't what users see unless they switch back. TV devices are unaffected (still the dedicated TV layout on the legacy app).
  • Plugin ABI break. The server now targets .NET 10, several plugin interfaces changed (search, alternate-versions/playlist storage, parts of IItemRepository/IUserManager), and the target ABI moved to 12.0.0.0. Any plugin built against 10.11 (net9.0) will not load at all — Jellyfin's own upgrade notes tell users to remove third-party plugins before upgrading and only re-add rebuilt versions.

Practical effect: a plugin (or theme) written against the old DOM/class structure targets a layout that most users no longer see by default, and a plugin binary built for 10.11 won't even load on a 12.0 server. Both the UI target and the plugin runtime changed at once.

3. Why old-style "skin" plugins broke

DOM/CSS surface changed

The Modern layout renders with React + MUI rather than the old server-rendered/jQuery views. Class names and structure are different, and MUI's styling layer is less friendly to blind CSS overrides than the old hand-written markup was — selectors written for Legacy mostly miss.

Plugin loading itself changed

Beyond styling, the mechanism plugins use to inject CSS/JS into index.html (the community "File Transformation" plugin, used as a dependency by most skin/home-screen plugins) was rebuilt from Harmony/MonoMod runtime patching to standard ASP.NET Core middleware for 12.0. A plugin depending on the old File Transformation build also won't function correctly even if it happens to load.

6. Recommended build plan

1

Stand up a disposable 12.0.0 test server

Don't develop against production. Confirm you're actually on 12.0.0 (not an RC) and do a hard refresh/cache clear after any web-client-affecting change — stale cached JS/CSS is the most common source of "it's not working" reports on this release.

2

Start with Custom CSS only, against the base theme variables

Inspect src/themes/_base's variable names (colors, backgrounds, accents) in the running client's devtools and re-point them before writing any raw selector overrides. This alone likely gets you most of the way to the reference palette/spacing.

3

Layer in File Transformation once CSS hits a wall

Install File Transformation 3.0.0.0 first, since Plugin Pages and Home Screen Sections both depend on it. Use it to inject the extra CSS/markup hooks the Custom CSS box can't reach (e.g. structural tweaks to the app bar).

4

Add Plugin Pages / Home Screen Sections only for behavior you actually need

If the goal is purely visual, you may not need either. If you want configurable home rows or a new settings page, add them — but verify the Modular Home settings page actually loads on your test server first, given the open 12.0 race-condition bug.

5

Scaffold your own plugin against the 12.0 SDK

.NET 10 SDK, target framework net10.0, reference Jellyfin.Controller/Jellyfin.Model 12.0.0 NuGet packages, and set targetAbi to 12.0.0.0 in your build manifest. Register your CSS/JS payload through File Transformation's callback mechanism (via reflection against its loaded assembly, per its own docs) rather than writing to index.html directly.

6

Only fork jellyfin-web if something in the reference UI truly can't be reached from CSS + File Transformation hooks

Keep this as a fallback, not a starting point — it trades a small, upgrade-safe plugin for full ownership of the client's build and future merges.

7. Prerequisites checklist

  • Jellyfin server confirmed at 12.0.0 (or later 12.x) — not 10.11.x.
  • .NET 10 SDK installed for any C# plugin work.
  • Node.js + npm only if you go as far as building/patching jellyfin-web source directly.
  • Third-party plugins removed/rebuilt: nothing built for 10.11 will load; check each dependency (File Transformation, Plugin Pages, Home Screen Sections, and anything else you plan to use) is on a 12.0-tagged release (all three are, as of 3.0.0.0).
  • A full data/config backup before touching a real server, and a full library scan after any server-version upgrade (12.0 requires this regardless of UI work).
  • Browser hard-refresh / cache clear as your default troubleshooting step while iterating.

8. Risks & open questions to test for early

  • Risk MUI's generated class names can be less stable across Jellyfin point releases than the old hand-written classes were — prefer the CSS-variable surface and stable semantic selectors (data attributes, aria roles) over deeply nested generated class chains where possible.
  • Risk Home Screen Sections' settings UI has an open, unresolved crash on 12.0.0 (API client race condition) as of this writing — don't assume the plugin path is trouble-free without testing it yourself first.
  • Risk Any other community skin/plugin you might want to combine with your own work needs its own confirmed 12.0/net10.0 build — mixed old/new plugins on one server has already caused at least one reported case of a stale-.NET-9 plugin taking down other plugins' startup tasks silently.
  • Open question: whether the hover-card synopsis text in the reference is available from a stock API call already reaching the client, or needs to be fetched/rendered via an injected component — worth checking against a live 12.0 instance's network tab before committing to an approach.
